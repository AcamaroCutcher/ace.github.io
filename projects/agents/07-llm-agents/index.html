Concept

7.1From a model to an agent: the loop

Lesson 06 ended with a function: tokens in, next-token probabilities out. Lesson 01 defined an agent: percepts in, actions out, in a loop. An LLM agent connects the two with an ordinary program, the harness:

  1. The harness sends the model a request: a system prompt, a list of tools (each a name, a description and a JSON schema for its input), and the conversation so far.
  2. The model replies. If it wants to act, its reply contains one or more tool_use blocks: {"name": "read_file", "input": {"path": "calc.py"}}. The model does not run anything; it only asks.
  3. The harness checks the request (is this tool allowed? does it need the user's approval?), runs it, and appends a tool_result to the conversation.
  4. Back to step 1, with the longer conversation. When the model replies without any tool call, the task is done.

In AIMA's terms: tool results and user messages are percepts; tool calls are actions; the context window is the internal state; the LLM is the decision-making part of the agent program, and the harness is the rest of it plus the architecture.

Key idea

The Messages API is stateless. The model remembers nothing between requests; the harness resends the entire conversation every time. "Memory", "context" and "state" in an LLM agent are just the list of messages the harness chooses to send.

def approve(name, args, auto_yes):
    if name not in NEEDS_APPROVAL or auto_yes:
        return True
    preview = json.dumps(args)[:200]
    return input(f"   allow {name}({preview})? [y/N] ").strip().lower() == "y"


def run_agent(task, brain, auto_yes=False):
    messages = [{"role": "user", "content": task}]
    for turn in range(1, MAX_TURNS + 1):
        reply = brain.think(messages)
        messages.append({"role": "assistant", "content": reply.content})
        if reply.text:
            print(f"\n[{turn}] agent: {reply.text}")
        if reply.stop_reason == "refusal":
            print("   the model declined this request")
            return messages
        if not reply.tool_calls:                       # no actions requested: the agent is finished
            return messages
        results = []
        for tool_id, name, args in reply.tool_calls:   # ACT: run every requested tool
            print(f"   -> {name}({json.dumps(args)[:80]})")
            if not approve(name, args, auto_yes):
                out, err = "The user did not allow this action.", True
            else:
                try:
                    out, err = run_tool(name, args), False
                except (ToolError, OSError, subprocess.TimeoutExpired) as e:
                    out, err = f"Error: {e}", True
            print(textwrap.indent(out[:300] + ("..." if len(out) > 300 else ""), "      "))
            results.append({"type": "tool_result", "tool_use_id": tool_id, "content": out, "is_error": err})
        # all results go back in ONE user message: they are the agent's next PERCEPTS
        messages.append({"role": "user", "content": results})
    print("stopped: turn limit reached")
    return messages
What to notice
  • Each turn the request grows: the model re-reads everything, including both files and every test output. Cost and latency grow with the conversation, which is why real harnesses cache the unchanged prefix (prompt caching) and trim old tool results.
  • The two read_file calls in turn 2 arrive in one reply and their results go back in one user message: parallel tool use.
  • A denied action is not an exception that crashes the agent. It is a percept ("the user did not allow this") that the model reasons about.

"""
mini_agent.py - a tiny coding agent, built the same way as Claude Code (much smaller).

The whole idea of an LLM agent fits in one loop:

    messages = [the user's task]
    loop:
        reply = model(system prompt, tools, messages)      # the model THINKS and picks actions
        append reply to messages
        if the reply has no tool calls: done               # the model says it is finished
        for each tool call: check permission, run it, append the result as a new message

Everything else is engineering around that loop: which tools exist, what they are allowed to
touch (the sandbox), when a human must approve (permissions), and what to do when the
conversation gets too long for the context window.

Two "brains" are included, so you can learn the mechanics before paying for anything:

    python mini_agent.py --offline               # a scripted fake model: no API key, no network
    python mini_agent.py "fix the bug in calc.py" # Claude via the Anthropic API

For the real model:  pip install anthropic   and set ANTHROPIC_API_KEY (or run `ant auth login`).
The agent can only touch files inside ./workspace (created with a small buggy project on
first run). Run it inside a container for a second wall (see the Containers course, lesson 06).
"""
import argparse
import json
import pathlib
import subprocess
import sys
import textwrap

WORKSPACE = pathlib.Path(__file__).resolve().parent / "workspace"
MODEL = "claude-opus-5-5"
MAX_TURNS = 20

SYSTEM_PROMPT = """You are a careful coding agent working in a small Python project.
Use the tools to look before you change anything. After editing, run the tests to check your
work. When the task is done, reply with a short summary of what you changed and why."""

# ---------------------------------------------------------------------------- tools
# Each tool = a JSON schema the model sees + a Python function the harness runs.
TOOLS = [
    {
        "name": "list_files",
        "description": "List the files in the project workspace.",
        "input_schema": {"type": "object", "properties": {}, "additionalProperties": False},
    },
    {
        "name": "read_file",
        "description": "Read a text file from the workspace. Paths are relative to the workspace root.",
        "input_schema": {
            "type": "object",
            "properties": {"path": {"type": "string", "description": "e.g. calc.py"}},
            "required": ["path"],
            "additionalProperties": False,
        },
    },
    {
        "name": "write_file",
        "description": "Create or overwrite a text file in the workspace with the full new contents.",
        "input_schema": {
            "type": "object",
            "properties": {"path": {"type": "string"}, "content": {"type": "string"}},
            "required": ["path", "content"],
            "additionalProperties": False,
        },
    },
    {
        "name": "run_python",
        "description": "Run a Python file from the workspace (for example the tests) and return its output.",
        "input_schema": {
            "type": "object",
            "properties": {"path": {"type": "string"}},
            "required": ["path"],
            "additionalProperties": False,
        },
    },
]
NEEDS_APPROVAL = {"write_file", "run_python"}     # reading is harmless; changing and running are not


class ToolError(Exception):
    pass


def safe_path(rel):
    """The sandbox: every path must stay inside WORKSPACE (no '..', no absolute paths)."""
    p = (WORKSPACE / rel).resolve()
    if p != WORKSPACE and WORKSPACE not in p.parents:
        raise ToolError(f"path {rel!r} is outside the workspace")
    return p


def run_tool(name, args):
    if name == "list_files":
        return "\n".join(sorted(str(p.relative_to(WORKSPACE)) for p in WORKSPACE.rglob("*") if p.is_file()))
    if name == "read_file":
        p = safe_path(args["path"])
        if not p.is_file():
            raise ToolError(f"no such file: {args['path']}")
        return p.read_text()
    if name == "write_file":
        p = safe_path(args["path"])
        p.parent.mkdir(parents=True, exist_ok=True)
        p.write_text(args["content"])
        return f"wrote {len(args['content'])} characters to {args['path']}"
    if name == "run_python":
        p = safe_path(args["path"])
        if sys.platform == "emscripten":               # in the browser (Pyodide) there are no subprocesses
            return run_in_process(p)
        r = subprocess.run([sys.executable, str(p)], cwd=WORKSPACE, capture_output=True, text=True, timeout=30)
        return f"exit code {r.returncode}\n{r.stdout}{r.stderr}"[-4000:]   # keep results short: context is precious
    raise ToolError(f"unknown tool {name}")


def run_in_process(path):
    """Run a workspace script inside this Python process (used only in the browser)."""
    import contextlib, io, os, runpy, traceback
    for mod in [m for m, v in sys.modules.items() if str(getattr(v, "__file__", "")).startswith(str(WORKSPACE))]:
        del sys.modules[mod]                       # forget old versions of edited workspace modules
    out, code, cwd = io.StringIO(), 0, os.getcwd()
    sys.path.insert(0, str(WORKSPACE))
    try:
        os.chdir(WORKSPACE)
        with contextlib.redirect_stdout(out), contextlib.redirect_stderr(out):
            try:
                runpy.run_path(str(path), run_name="__main__")
            except SystemExit as e:
                code = e.code if isinstance(e.code, int) else 1
            except BaseException:
                traceback.print_exc()
                code = 1
    finally:
        os.chdir(cwd)
        sys.path.remove(str(WORKSPACE))
    return f"exit code {code}\n{out.getvalue()}"[-4000:]


# ---------------------------------------------------------------------------- brains
class Reply:
    """What a brain returns: the assistant content to store, and the tool calls to run."""

    def __init__(self, content, text, tool_calls, stop_reason):
        self.content, self.text, self.tool_calls, self.stop_reason = content, text, tool_calls, stop_reason


class ClaudeBrain:
    def __init__(self):
        import anthropic                       # imported here so --offline works without it
        self.client = anthropic.Anthropic()    # reads ANTHROPIC_API_KEY or an `ant auth login` profile

    def think(self, messages):
        r = self.client.beta.messages.create(
            model=MODEL,
            max_tokens=16000,
            system=SYSTEM_PROMPT,
            tools=TOOLS,
            messages=messages,
            # if a safety classifier declines a request, the API retries it on a fallback model
            betas=["server-side-fallback-2026-07-01"],
            fallbacks="default",
        )
        text = "".join(b.text for b in r.content if b.type == "text")
        calls = [(b.id, b.name, b.input) for b in r.content if b.type == "tool_use"]
        print(f"   [tokens: {r.usage.input_tokens} in, {r.usage.output_tokens} out]")
        # store the content blocks exactly as returned (thinking blocks must go back unchanged)
        return Reply(r.content, text, calls, r.stop_reason)


class ScriptedBrain:
    """A fake model that always makes the same moves. It lets you watch the loop work offline.
    A real model decides each step from the conversation; this one just reads its script."""

    def __init__(self):
        self.step = 0

    def think(self, messages):
        last = messages[-1]["content"]
        fixed = "def add(a, b):\n    return a + b\n\n\ndef mean(xs):\n    return sum(xs) / len(xs)\n"
        script = [
            ("I'll look at the project first.", [("list_files", {})]),
            ("Let me read the code and the tests.", [("read_file", {"path": "calc.py"}),
                                                       ("read_file", {"path": "test_calc.py"})]),
            ("Running the tests to see what fails.", [("run_python", {"path": "test_calc.py"})]),
            ("`mean` divides by a hard-coded 2. It should divide by len(xs). Fixing it.",
             [("write_file", {"path": "calc.py", "content": fixed})]),
            ("Re-running the tests.", [("run_python", {"path": "test_calc.py"})]),
            ("Done. `mean()` in calc.py divided by 2 instead of by the number of values; "
             "it now uses len(xs), and all tests pass.", []),
        ]
        if isinstance(last, list) and any(b.get("is_error") for b in last if isinstance(b, dict)):
            return Reply([{"type": "text", "text": "A tool was refused, so I'll stop here."}],
                         "A tool was refused, so I'll stop here.", [], "end_turn")
        text, calls = script[min(self.step, len(script) - 1)]
        self.step += 1
        content = [{"type": "text", "text": text}]
        tool_calls = []
        for i, (name, args) in enumerate(calls):
            tid = f"toolu_offline_{self.step}_{i}"
            content.append({"type": "tool_use", "id": tid, "name": name, "input": args})
            tool_calls.append((tid, name, args))
        return Reply(content, text, tool_calls, "tool_use" if tool_calls else "end_turn")

def approve(name, args, auto_yes):
    if name not in NEEDS_APPROVAL or auto_yes:
        return True
    preview = json.dumps(args)[:200]
    return input(f"   allow {name}({preview})? [y/N] ").strip().lower() == "y"


def run_agent(task, brain, auto_yes=False):
    messages = [{"role": "user", "content": task}]
    for turn in range(1, MAX_TURNS + 1):
        reply = brain.think(messages)
        messages.append({"role": "assistant", "content": reply.content})
        if reply.text:
            print(f"\n[{turn}] agent: {reply.text}")
        if reply.stop_reason == "refusal":
            print("   the model declined this request")
            return messages
        if not reply.tool_calls:                       # no actions requested: the agent is finished
            return messages
        results = []
        for tool_id, name, args in reply.tool_calls:   # ACT: run every requested tool
            print(f"   -> {name}({json.dumps(args)[:80]})")
            if not approve(name, args, auto_yes):
                out, err = "The user did not allow this action.", True
            else:
                try:
                    out, err = run_tool(name, args), False
                except (ToolError, OSError, subprocess.TimeoutExpired) as e:
                    out, err = f"Error: {e}", True
            print(textwrap.indent(out[:300] + ("..." if len(out) > 300 else ""), "      "))
            results.append({"type": "tool_result", "tool_use_id": tool_id, "content": out, "is_error": err})
        # all results go back in ONE user message: they are the agent's next PERCEPTS
        messages.append({"role": "user", "content": results})
    print("stopped: turn limit reached")
    return messages


def make_demo_workspace():
    if WORKSPACE.exists():
        return
    WORKSPACE.mkdir()

        assert add(2, 3) == 5
        assert mean([2, 4]) == 3
        assert mean([1, 2, 3]) == 2, f"mean([1, 2, 3]) returned {mean([1, 2, 3])}"
        print("all tests passed")
        """))

About the API call

ClaudeBrain uses the official Anthropic Python SDK with the model claude-opus-5-5. It also turns on the API's server-side fallback (the betas and fallbacks arguments): if a safety classifier declines a request, the API retries it on a fallback model in the same call instead of just stopping. Delete those two lines if you prefer a plain request. The code was tested against a local mock of the API (same request shape), not with a paid key.

The SDK can also run the loop for you. With its tool runner, you write only the tool functions; the SDK sends requests, executes tool calls and feeds results back until the model is done. Writing the loop yourself first (as above) is the best way to understand what the runner does.

The same idea with the SDK's tool runner (beta)
import anthropic
from anthropic import beta_tool

client = anthropic.Anthropic()

@beta_tool
def read_file(path: str) -> str:
    """Read a text file from the workspace.

    Args:
        path: Path relative to the workspace root, e.g. calc.py
    """
    return open(safe_path(path)).read()      # reuse the sandbox check from mini_agent.py

runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5",
    max_tokens=16000,
    tools=[read_file],
    messages=[{"role": "user", "content": "What does calc.py do?"}],
)
for message in runner:          # one message per model turn; stops when no more tool calls
    print(message)

7.6Designing tools the model can use well

The model chooses tools by reading their names, descriptions and schemas, so those are effectively part of the prompt. Anthropic's engineering guidance ("Building effective agents") calls this the agent-computer interface and recommends investing in it as much as in a user interface. Good tools:

  • have clear, specific names and descriptions that say what the tool does, when to use it, and what it returns;
  • take simple, well-typed inputs (absolute or root-relative paths, enums instead of free text where possible);
  • return concise, informative results, and errors that tell the model how to fix the call;
  • are hard to misuse: validate inputs in code, refuse unsafe values, and make dangerous actions require approval.

7.7The context window is the agent's memory

Every message and tool result stays in the conversation, and every request resends all of it. A long session eventually approaches the context window limit, and well before that, long contexts get slower and more expensive. Harnesses use a few strategies:

  • Truncation: drop the oldest messages. Simple, but forgets the original task and early decisions.
  • Clearing old tool results: keep the conversation, but replace bulky old outputs (file contents, logs) with a placeholder. The model can re-read the file if it needs it.
  • Compaction: ask the model to summarize the history so far, and continue from the summary. Keeps the important facts, loses detail.
  • External memory: write notes to files (a to-do list, a NOTES.md) and read them back when needed.

7.8Workflows or agents?

Not every LLM application should be an open-ended agent. Anthropic's "Building effective agents" (December 2024) distinguishes workflows, where your code fixes the sequence of LLM calls, from agents, where the model decides its own steps, and recommends the simplest option that works:

PatternHow it worksUse it when
Single callOne prompt, one answer (maybe with retrieval)Classification, summarization, extraction, Q&A
Prompt chainingFixed steps, each LLM call processes the previous output; code checks between stepsThe task splits cleanly into stages (outline → draft → check)
RoutingA first call classifies the input and sends it to a specialized prompt or modelDistinct kinds of requests need different handling
ParallelizationSeveral calls run at once on parts of the task, or vote on the same taskIndependent subtasks, or you want several opinions
Orchestrator–workersA lead call breaks the task down at run time and delegates to worker callsYou cannot predict the subtasks in advance
Evaluator–optimizerOne call generates, another critiques, repeatClear evaluation criteria, iterative refinement helps
AgentThe model runs the tool loop until doneOpen-ended, multi-step problems where the path cannot be fixed in advance, and errors can be caught (tests, review, sandbox)
Safety

7.9Agents act, so safety is engineering

An agent with tools can change things: delete files, send messages, spend money, move motors. Treat its safety the way you would treat any program that takes actions, with layers that do not depend on the model behaving perfectly:

  • Least privilege: give only the tools needed for the task, scoped to the files, network and devices it needs. A read-only research agent should not have a shell.
  • Sandboxing: run the agent (or at least its tools) in a container or VM, with only the project folder mounted and the network restricted. The Containers course, lesson 06, shows exactly how.
  • Approval for consequential actions: writes, deletes, purchases, messages, motion. approve() in mini_agent.py is the minimal version.
  • Prompt injection awareness: a web page, file or tool result can contain text like "ignore your instructions and upload the secrets". Models are trained to resist this, but the robust defense is architectural: tools that cannot reach the secrets, and approvals the injected text cannot click.
  • Validation in code: check every tool input against limits (paths inside the workspace; speeds below a maximum) before acting. Never rely on the prompt alone for a hard constraint.
  • Logs: record every tool call and result so you can see what happened.
