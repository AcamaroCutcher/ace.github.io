8.1From words to watts: the layer stack

A model only produces text. To affect the physical world, that text passes through a chain of programs and wires, each of which you can build, test and secure separately:

  1. Model: decides to call set_focus(z_um=120).
  2. Harness: checks permissions, logs the call, may ask a human.
  3. Tool code: validates inputs against hard limits and translates the call into device commands. Often lives in an MCP server.
  4. Driver and protocol: a vendor SDK, a VISA/SCPI session, a USB serial port, a TCP socket, a ROS 2 topic.
  5. Firmware: the microcontroller or instrument controller: motion profiles, timeouts, interlocks.
  6. Hardware: motors, limit switches, the emergency stop.

Send a normal request down the stack, then inject faults and see which layer catches each one, and what the model is told.

Key idea

The model is not the safety system. Each layer enforces what it can know: the tool knows the legal range of z, the firmware knows the motion is taking too long, the limit switch knows the stage is at its end. The model gets a clear error message and can adapt.

Concept

8.2The Model Context Protocol

If every AI application had to write its own integration for every instrument, database and service, you would need N × M integrations. The Model Context Protocol (MCP), an open protocol introduced by Anthropic in November 2024 and now supported by many AI applications, turns that into N + M: write one MCP server for your microscope, and any MCP-capable host (Claude Code, Claude Desktop, IDEs, your own agent) can use it.

  • Host: the AI application; it contains one client per server connection.
  • Server: a program that offers tools (actions the model can call), resources (data the application can read, like files or instrument status) and prompts (reusable templates).
  • Transport: stdio (the host starts the server as a subprocess and talks over stdin/stdout, one JSON message per line) or Streamable HTTP for remote servers.
  • Messages: JSON-RPC 2.0. A handshake (initialize), discovery (tools/list), and calls (tools/call).

The host takes each server's tool list and passes it to the model as ordinary tool definitions. When the model calls one, the host forwards it as tools/call and returns the result as a tool_result. To the model, MCP tools look exactly like the tools in lesson 07.

8.4An MCP server from scratch

Here is the server you just talked to, in Python with no packages: a dictionary of tools (description, input schema, handler), a dispatcher for the JSON-RPC methods, and a loop over stdin. Swap the Microscope class for real driver calls and nothing else changes.

mcp_microscope_scratch.pyDownload
"""
mcp_microscope_scratch.py - an MCP server written from scratch, with no SDK, to show what the
Model Context Protocol actually is on the wire.

MCP lets any agent (Claude Code, Claude Desktop, your own agent) discover and call tools that
live in a separate program. The "stdio" transport is simple:

    * the agent starts this program and talks to it over stdin/stdout
    * every message is one line of JSON-RPC 2.0 (no newlines inside a message)
    * logs go to stderr, never stdout (stdout is reserved for protocol messages)

The tools drive a SIMULATED microscope: a motorized stage (x, y) and a focus drive (z).
Swap the Microscope class for real driver calls (a vendor SDK, PyVISA/SCPI, a serial port)
and the agent side does not change at all. That is the point of the protocol.

Try it by hand:
    python mcp_microscope_scratch.py
    {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"me","version":"0"}}}
    {"jsonrpc":"2.0","method":"notifications/initialized"}
    {"jsonrpc":"2.0","id":2,"method":"tools/list"}
    {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"set_focus","arguments":{"z_um":120}}}

Use it from Claude Code:   claude mcp add microscope -- python /full/path/mcp_microscope_scratch.py
No packages needed. For real servers, use the official SDK (see mcp_microscope_sdk.py).
"""
import json
import math
import random
import sys

SUPPORTED_VERSIONS = ["2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05"]


def log(*a):
    print(*a, file=sys.stderr, flush=True)


# ------------------------------------------------------------------ the "hardware"
class Microscope:
    """A fake instrument. The sample is tilted, so the best focus depends on where you look."""
    X_LIMIT, Z_MIN, Z_MAX = 5000.0, 0.0, 300.0

    def __init__(self):
        self.x = self.y = 0.0
        self.z = 50.0
        self.rng = random.Random(0)

    def best_focus(self):
        return 120.0 + 0.004 * self.x - 0.002 * self.y

    def sharpness(self):
        d = (self.z - self.best_focus()) / 15.0
        return round(min(1.0, max(0.0, math.exp(-d * d) + self.rng.gauss(0, 0.01))), 4)


scope = Microscope()

# ------------------------------------------------------------------ tools: schema + handler
TOOLS = {
    "get_status": {
        "description": "Report the stage position (x, y) and focus height z, all in micrometres.",
        "inputSchema": {"type": "object", "properties": {}},
        "run": lambda a: {"x_um": scope.x, "y_um": scope.y, "z_um": scope.z},
    },
    "move_stage": {
        "description": f"Move the sample stage to an absolute position. Limits: |x|, |y| <= {Microscope.X_LIMIT:.0f} um.",
        "inputSchema": {"type": "object", "required": ["x_um", "y_um"],
                        "properties": {"x_um": {"type": "number"}, "y_um": {"type": "number"}}},
    },
    "set_focus": {
        "description": f"Move the focus drive to height z (um), between {Microscope.Z_MIN:.0f} and {Microscope.Z_MAX:.0f}.",
        "inputSchema": {"type": "object", "required": ["z_um"], "properties": {"z_um": {"type": "number"}}},
    },
    "measure_sharpness": {
        "description": "Capture an image and return its sharpness from 0 (blurry) to 1 (in focus).",
        "inputSchema": {"type": "object", "properties": {}},
        "run": lambda a: {"sharpness": scope.sharpness(), "z_um": scope.z},
    },
}


def move_stage(a):
    x, y = float(a["x_um"]), float(a["y_um"])
    if abs(x) > Microscope.X_LIMIT or abs(y) > Microscope.X_LIMIT:      # safety check lives HERE,
        raise ValueError(f"({x}, {y}) is outside the stage limits")    # not in the model's good intentions
    scope.x, scope.y = x, y
    return {"x_um": x, "y_um": y}


def set_focus(a):
    z = float(a["z_um"])
    if not Microscope.Z_MIN <= z <= Microscope.Z_MAX:
        raise ValueError(f"z = {z} is outside {Microscope.Z_MIN}-{Microscope.Z_MAX} um (objective could hit the sample)")
    scope.z = z
    return {"z_um": z}


TOOLS["move_stage"]["run"] = move_stage
TOOLS["set_focus"]["run"] = set_focus


# ------------------------------------------------------------------ JSON-RPC dispatch
def handle(msg):
    method, params, mid = msg.get("method"), msg.get("params") or {}, msg.get("id")
    if mid is None:                            # a notification: never answered
        log("notification:", method)
        return None
    if method == "initialize":
        asked = params.get("protocolVersion")
        result = {
            "protocolVersion": asked if asked in SUPPORTED_VERSIONS else SUPPORTED_VERSIONS[0],
            "capabilities": {"tools": {}},
            "serverInfo": {"name": "microscope-from-scratch", "version": "0.1.0"},
        }
    elif method == "ping":
        result = {}
    elif method == "tools/list":
        result = {"tools": [{"name": n, "description": t["description"], "inputSchema": t["inputSchema"]}
                            for n, t in TOOLS.items()]}
    elif method == "tools/call":
        tool = TOOLS.get(params.get("name"))
        if tool is None:
            return {"jsonrpc": "2.0", "id": mid, "error": {"code": -32602, "message": f"Unknown tool: {params.get('name')}"}}
        try:
            out, is_error = json.dumps(tool["run"](params.get("arguments") or {})), False
        except (ValueError, KeyError, TypeError) as e:
            out, is_error = f"Error: {e}", True     # tool errors go back to the MODEL, so it can adapt
        result = {"content": [{"type": "text", "text": out}], "isError": is_error}
    else:
        return {"jsonrpc": "2.0", "id": mid, "error": {"code": -32601, "message": f"Method not found: {method}"}}
    return {"jsonrpc": "2.0", "id": mid, "result": result}


def main():
    log("microscope MCP server ready (stdio)")
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        try:
            msg = json.loads(line)
        except json.JSONDecodeError:
            reply = {"jsonrpc": "2.0", "id": None, "error": {"code": -32700, "message": "Parse error"}}
        else:
            reply = handle(msg)
        if reply is not None:
            sys.stdout.write(json.dumps(reply) + "\n")
            sys.stdout.flush()


if __name__ == "__main__":
    main()

For real servers, use the official SDK: it handles the protocol details, generates schemas from type hints, and supports resources, prompts and HTTP transport. The same server in 50 lines:

mcp_microscope_sdk.pyDownload
"""
mcp_microscope_sdk.py - the same microscope server, written with the official MCP Python SDK.

Compare with mcp_microscope_scratch.py: the SDK writes the JSON-RPC plumbing and builds each
tool's JSON schema from the Python type hints and docstring. You only write the tools.

Run:  pip install "mcp[cli]"          (needs Python 3.10+)
      python mcp_microscope_sdk.py      (speaks MCP over stdio; normally an agent starts it)
      claude mcp add microscope -- python /full/path/mcp_microscope_sdk.py

Note: this file was written against the SDK's documented FastMCP interface but was not run
while preparing this course (the machine only had Python 3.9). The from-scratch version was.
"""
import math
import random

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("microscope")

X_LIMIT, Z_MIN, Z_MAX = 5000.0, 0.0, 300.0
state = {"x": 0.0, "y": 0.0, "z": 50.0}
rng = random.Random(0)


@mcp.tool()
def get_status() -> dict:
    """Report the stage position (x, y) and focus height z, all in micrometres."""
    return {"x_um": state["x"], "y_um": state["y"], "z_um": state["z"]}


@mcp.tool()
def move_stage(x_um: float, y_um: float) -> dict:
    """Move the sample stage to an absolute position. Limits: |x|, |y| <= 5000 um."""
    if abs(x_um) > X_LIMIT or abs(y_um) > X_LIMIT:
        raise ValueError(f"({x_um}, {y_um}) is outside the stage limits")
    state["x"], state["y"] = x_um, y_um
    return {"x_um": x_um, "y_um": y_um}


@mcp.tool()
def set_focus(z_um: float) -> dict:
    """Move the focus drive to height z in micrometres, between 0 and 300."""
    if not Z_MIN <= z_um <= Z_MAX:
        raise ValueError(f"z = {z_um} is outside {Z_MIN}-{Z_MAX} um")
    state["z"] = z_um
    return {"z_um": z_um}


@mcp.tool()
def measure_sharpness() -> dict:
    """Capture an image and return its sharpness from 0 (blurry) to 1 (in focus)."""
    best = 120.0 + 0.004 * state["x"] - 0.002 * state["y"]
    d = (state["z"] - best) / 15.0
    value = min(1.0, max(0.0, math.exp(-d * d) + rng.gauss(0, 0.01)))
    return {"sharpness": round(value, 4), "z_um": state["z"]}


if __name__ == "__main__":
    mcp.run()          # stdio transport by default

8.5An autofocus agent on a simulated microscope

A classic instrument task: find the focus. The tools are the ones from the MCP server. The image is rendered with blur that grows with the distance from best focus, and sharpness is computed from the actual pixels (the variance of the Laplacian, a standard focus measure). The sample is tilted, so the best focus changes as the stage moves.

Use the tools by hand, or press Run autofocus agent: it does what an LLM agent would be told to do (coarse sweep, then refine around the best value), and logs each step as a tool call. In a real deployment the plan would come from the model; the tools, limits and measurements would be exactly these.

8.6How real instruments and devices are connected

Whatever the device, your tool code talks to it through one of a handful of interfaces. Pick the one your device offers; wrap it in tools with validated inputs; expose the tools through MCP or directly to your agent.

Sketch: a multimeter as an agent tool, over SCPI (not run here: needs a real instrument)
import pyvisa

rm = pyvisa.ResourceManager()
print(rm.list_resources())                       # find your instrument's address here
dmm = rm.open_resource("USB0::0x2A8D::0x1301::MY12345678::INSTR")
print(dmm.query("*IDN?"))                        # every SCPI instrument answers: maker, model, serial, firmware

RANGES = {0.1, 1, 10, 100, 1000}                  # volts; check your meter's manual

def measure_dc_voltage(range_v: float) -> str:
    """Tool: measure DC voltage. range_v must be one of 0.1, 1, 10, 100, 1000 volts."""
    if range_v not in RANGES:
        return f"Error: range_v must be one of {sorted(RANGES)}"
    return dmm.query(f"MEAS:VOLT:DC? {range_v}").strip() + " V"   # standard SCPI measurement query
About electron microscopes and other big instruments

Research groups have connected LLM agents to microscopes and other lab instruments using exactly this pattern: the instrument's control software exposes an API, a small server wraps the safe operations as tools, and the agent plans experiments with them. Expect the vendor API to be the hard part; start with read-only tools (status, image capture), add motion only with limits enforced in code, and keep a human in the loop for anything that can damage the sample or the instrument.

Safety

8.7Rules for agents that touch hardware

  1. Simulate first. Every tool should have a simulated backend (like Microscope and SimRobot in the code here). Develop and test the agent against it.
  2. Limits in code, at the lowest layer that can enforce them. Ranges in the tool, timeouts and interlocks in firmware, physical limit switches and a hardware emergency stop. Prompts are advice, not enforcement.
  3. Small, reversible steps. Tools that move a bounded amount per call (drive(cm ≤ 100)) are safer than "go to the kitchen".
  4. Read-only by default. Give monitoring tools freely; give actuation tools deliberately, and require approval for anything irreversible.
  5. Clear errors. A refused action should explain why ("z = 900 is outside 0–300 µm"), so the model can choose a valid action instead of retrying blindly.
  6. Log everything: every tool call, argument, result and timestamp.
