Parallel processing: OpenMP and MPI

Threads on one machine with OpenMP, processes across a cluster with MPI, domain decomposition and halo exchange as in FIRETEC, and job scripts.

Two kinds of parallelism

Shared memory (OpenMP)Distributed memory (MPI)
What runsseveral threads of one programseveral copies of the program (processes), one per core
Memoryall threads see the same arrayseach process has its own; data moves only in messages
Scaleone node (tens of cores)thousands of cores on many nodes
Effortadd directives to loopssplit the data and write the communication
In FIRETECnot usedthe whole code: the grid is split over nprocx × nprocy processes

No program speeds up forever. If a fraction f of the work is serial, P processors give at most a speed-up of 1 / (f + (1 − f)/P) (Amdahl's law): with 5% serial work, 64 cores give at most 15×. In grid codes the limit is usually communication: each step, every block must swap its edges with its neighbours.

OpenMP: parallel loops

omp_sum.f90
! omp_sum.f90 -- shared-memory parallel loops with OpenMP
! build:  gfortran -O2 -fopenmp omp_sum.f90 -o omp_sum
! run:    OMP_NUM_THREADS=4 ./omp_sum
program omp_sum
  use omp_lib
  implicit none
  integer, parameter :: wp = kind(1.0d0), n = 50000000
  real(wp), allocatable :: rhof(:), rate(:)
  real(wp) :: total, t0, t1
  integer :: i

  allocate(rhof(n), rate(n))

  !$omp parallel do
  do i = 1, n                                   ! iterations are split between the threads
    rhof(i) = 0.7_wp
    rate(i) = 1.0e-3_wp * mod(i, 7)
  end do
  !$omp end parallel do

  t0 = omp_get_wtime()
  total = 0.0_wp
  !$omp parallel do reduction(+:total)
  do i = 1, n                                   ! each thread keeps a private partial sum, added at the end
    rhof(i) = max(0.0_wp, rhof(i) - 0.4552_wp * rate(i) * 0.1_wp)
    total = total + rhof(i)
  end do
  !$omp end parallel do
  t1 = omp_get_wtime()

  print '(a, i3)', 'threads:   ', omp_get_max_threads()
  print '(a, f14.4)', 'fuel left: ', total
  print '(a, f8.4, a)', 'loop time: ', t1 - t0, ' s'
end program omp_sum

Download omp_sum.f90

!$omp lines are comments to a compiler without -fopenmp, so the same file builds serially. The reduction(+:total) clause gives each thread a private copy of total and adds them at the end; without it, threads would overwrite each other's sums (a race condition). Try 1, 2, 4 and 8 threads: a loop this simple soon stops speeding up because it is limited by memory bandwidth, not arithmetic.

MPI: many processes

mpi_hello.f90
! mpi_hello.f90 -- every process runs the same program; MPI gives each one a rank
! build:  mpif90 mpi_hello.f90 -o mpi_hello
! run:    mpirun -np 4 ./mpi_hello
program mpi_hello
  use mpi
  implicit none
  integer :: rank, nprocs, ierror

  call MPI_Init(ierror)
  call MPI_Comm_rank(MPI_COMM_WORLD, rank, ierror)     ! who am I?        0 .. nprocs-1
  call MPI_Comm_size(MPI_COMM_WORLD, nprocs, ierror)   ! how many of us?
  print '(a, i3, a, i3)', 'Hello from rank', rank, ' of', nprocs
  call MPI_Finalize(ierror)
end program mpi_hello

Download mpi_hello.f90

Run it a few times: the order of the lines changes, because the processes run independently. MPI programs follow the single program, multiple data pattern: every process runs the same code and uses its rank to decide which part of the data is its own.

Domain decomposition and halo exchange

This is the core of FIRETEC's parallelism. The grid is cut into blocks; each process allocates its block plus a frame of halo cells that hold copies of its neighbours' edge values. Before each stencil update, the halos are refreshed with messages. Here is the same idea on a 1-D rod:

mpi_heat.f90
! mpi_heat.f90 -- domain decomposition with halo (ghost) cells, the pattern FIRETEC uses in msga.F90 and update.F90.
! A 1-D rod of N cells is split into equal pieces, one per process. Each step, every process swaps its edge
! values with its neighbours (MPI_Sendrecv), updates its own cells, and all processes agree on the maximum (MPI_Allreduce).
! build:  mpif90 -O2 mpi_heat.f90 -o mpi_heat
! run:    mpirun -np 4 ./mpi_heat
program mpi_heat
  use mpi
  implicit none
  integer, parameter :: wp = kind(1.0d0), n = 1200, ih = 1
  real(wp), parameter :: r = 0.4_wp                     ! kappa*dt/dx^2 <= 0.5 for stability
  real(wp), allocatable :: t(:), tnew(:)
  integer :: rank, nprocs, ierror, np, i0, left, right, step, i
  integer :: status(MPI_STATUS_SIZE)
  real(wp) :: local_max, global_max, local_sum, global_sum

  call MPI_Init(ierror)
  call MPI_Comm_rank(MPI_COMM_WORLD, rank, ierror)
  call MPI_Comm_size(MPI_COMM_WORLD, nprocs, ierror)
  if (mod(n, nprocs) /= 0) then                          ! FIRETEC makes the same check on n/nprocx
    if (rank == 0) print *, 'n must be divisible by the number of processes'
    call MPI_Abort(MPI_COMM_WORLD, 1, ierror)
  end if
  np = n / nprocs                                        ! cells owned by this process
  i0 = rank * np                                         ! global index of cell 0 (the left ghost)
  left = rank - 1; right = rank + 1
  if (rank == 0) left = MPI_PROC_NULL                    ! no neighbour: MPI skips the transfer
  if (rank == nprocs - 1) right = MPI_PROC_NULL

  allocate(t(1-ih:np+ih), tnew(np))
  t = 300.0_wp
  do i = 1, np                                           ! a hot slab in the middle of the global rod
    if (abs(i0 + i - n / 2) < n / 20) t(i) = 1000.0_wp
  end do

  do step = 1, 2000
    ! halo exchange: send my last cell right while receiving my left ghost, then the reverse
    call MPI_Sendrecv(t(np), 1, MPI_DOUBLE_PRECISION, right, 1, &
                      t(0),  1, MPI_DOUBLE_PRECISION, left,  1, MPI_COMM_WORLD, status, ierror)
    call MPI_Sendrecv(t(1),    1, MPI_DOUBLE_PRECISION, left,  2, &
                      t(np+1), 1, MPI_DOUBLE_PRECISION, right, 2, MPI_COMM_WORLD, status, ierror)
    if (rank == 0) t(0) = 300.0_wp                       ! physical boundaries on the outer edges
    if (rank == nprocs - 1) t(np + 1) = 300.0_wp
    do i = 1, np
      tnew(i) = t(i) + r * (t(i - 1) - 2.0_wp * t(i) + t(i + 1))
    end do
    t(1:np) = tnew
  end do

  local_max = maxval(t(1:np)); local_sum = sum(t(1:np))
  call MPI_Allreduce(local_max, global_max, 1, MPI_DOUBLE_PRECISION, MPI_MAX, MPI_COMM_WORLD, ierror)
  call MPI_Allreduce(local_sum, global_sum, 1, MPI_DOUBLE_PRECISION, MPI_SUM, MPI_COMM_WORLD, ierror)
  print '(a, i3, a, i5, a, i5, a, f8.2)', 'rank', rank, ' owns cells', i0 + 1, ' to', i0 + np, ', local max', local_max
  if (rank == 0) then
    print '(a, f8.2, a)', 'global max after 2000 steps: ', global_max, ' K'
    print '(a, f8.2, a)', 'mean temperature:            ', global_sum / n, ' K'
  end if
  call MPI_Finalize(ierror)
end program mpi_heat

Download mpi_heat.f90

MPI_Sendrecv sends and receives in one call, which avoids the deadlock of two processes both waiting to receive first. MPI_PROC_NULL as a neighbour turns the transfer into a no-op at the ends. MPI_Allreduce combines a value from every process (here the maximum and the sum) and gives the result to all of them. The answer does not depend on the number of processes.

FIRETEC does the same in 2-D. msga.F90 computes each process's block and its eight neighbours (left, right, above, below and the corners), wrapping around for cyclic boundaries:

FIRETEC-1.5.1, msga.F90 (excerpt)
  np=n/nprocx    !number of cells per processor in the x direction
  mp=m/nprocy    !number of cells per processor in the y direction
  npos = mod((mpi_rank+nprocx),nprocx)+1
  mpos = mpi_rank/nprocx+1
  ! set up neighbor information
  peleft=mpi_rank-1
  if (peleft<((mpos-1)*nprocx)) peleft=mpi_rank+(nprocx-1)
  peright=mpi_rank+1
  if (peright>(mpos*nprocx-1)) peright=mpi_rank-(nprocx-1)
  peabove=mpi_rank+nprocx
  if (peabove>(numprocs-1)) peabove=npos-1
  pebelow=mpi_rank-nprocx
  if (pebelow<0) pebelow=mpi_rank+((nprocy-1)*nprocx)
and update.F90 packs a strip of halo-width rows into a buffer and swaps it:

Running on a cluster

job.slurm
#!/bin/bash
#SBATCH --job-name=mpi_heat
#SBATCH --nodes=1
#SBATCH --ntasks=4
#SBATCH --time=00:05:00
#SBATCH --output=mpi_heat_%j.out
# Module names differ between clusters: run "module avail" to see yours.
module load gcc openmpi
mpif90 -O2 mpi_heat.f90 -o mpi_heat
srun ./mpi_heat

Download job.slurm

Submit with sbatch job.slurm and watch the queue with squeue -u $USER. For FIRETEC the number of tasks must equal nprocx × nprocy from the input file, and the grid must divide evenly between them.

Beyond MPI. Fortran 2008 coarrays build parallelism into the language (real :: t(n)[*]), and do concurrent loops or OpenACC directives let compilers such as nvfortran run loops on GPUs.

Exercises
  1. Run mpi_heat with 1, 2, 3, 4 and 6 processes and check that the global maximum is identical. Why must n be divisible by the process count?
  2. Remove the second MPI_Sendrecv. What goes wrong, and where in the rod?
  3. Time omp_sum with 1 to 8 threads and plot the speed-up against Amdahl's law.
  4. Extend mpi_heat.f90 to 2-D with an nprocx × nprocy layout using MPI_Cart_create and MPI_Cart_shift, and compare with FIRETEC's hand-made neighbour logic.
