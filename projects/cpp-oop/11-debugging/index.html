Debugging with GDB and sanitizers

A debugger lets you stop a running program, step through it line by line and look inside objects: the best way to see virtual dispatch happen, and the fastest way to find out why a program does something you did not intend.

GDB playground

Each mission is a small program with one bug. Mission 1 should print a total area of π + 2·3 = 9.14159 and prints 7.14159. Mission 2 should print 4 + 6 = 10 and prints 4. Find out why with the debugger.

The terminal accepts real GDB commands: break, run, next, step, finish, continue, print, display, watch, bt, up/down, info locals, info vtbl, ptype, list and more (type help). Enter on an empty line repeats the last command, as in GDB. Click a line number to toggle a breakpoint.

How this works GDB cannot run inside a web page, so this is a replay. Each program (buggy and fixed) was compiled with -g -O0 and stepped through line by line under a real debugger (LLDB, on an Apple Silicon Mac). Every value, address, call stack, vtable entry and return value you see was recorded from that run; the terminal reproduces how GDB formats them. Because it is a recording, you cannot change variables, and addresses on your machine will differ. Download debug_me.cpp and debug_me2.cpp to try them in a real debugger.

Sanitizers: let the compiler instrument your program

Some bugs do not misbehave visibly: reading a deleted object may print a plausible number. AddressSanitizer (-fsanitize=address, in GCC and Clang) adds checks to every memory access and stops at the first invalid one, with three stack traces: where the bad access happened, where the memory was freed, and where it was allocated.

asan_demo.cppRun online ↗
// asan_demo.cpp -- a dangling pointer to a polymorphic object, caught by AddressSanitizer
// build: -fsanitize=address -g -O0
// expect: crash
#include <iostream>
#include <memory>
#include <vector>

struct Shape { virtual ~Shape() = default; virtual double area() const = 0; };
struct Circle : Shape {
    double r;
    explicit Circle(double r) : r(r) {}
    double area() const override { return 3.14159 * r * r; }
};

int main() {
    std::vector<std::unique_ptr<Shape>> shapes;
    shapes.push_back(std::make_unique<Circle>(1));
    Shape* first = shapes[0].get();         // a non-owning pointer...
    shapes.clear();                          // ...and the owner destroys the object
    std::cout << first->area() << '\n';      // use after free: reads the vptr of a deleted object
}

Download asan_demo.cpp compiled with -std=c++17 -Wall -Wextra -fsanitize=address -g -O0

Read the report from the top: heap-use-after-free at line 20 (calling area() reads the deleted object's vptr), the memory was freed at line 19 by shapes.clear(), and it was allocated at line 17. The program runs about twice as slowly with ASan, so use it in testing, not in production. Its companion -fsanitize=undefined catches integer overflow, invalid casts and other undefined behavior.

Warnings worth turning on

The cheapest debugger is the compiler. Mission 2's bug is flagged at compile time by Clang's -Wall ('Triangle::area' hides overloaded virtual function); several pitfalls in lesson 10 are too.

FlagCatches
-Wall -Wextrathe common set: unused variables, sign comparisons, missing returns, and much more
-Woverloaded-virtuala derived function that hides a virtual one instead of overriding it (in Clang's -Wall; add it explicitly for GCC)
-Wnon-virtual-dtora class with virtual functions but a non-virtual destructor
-Wsuggest-overridean override not marked override
-Wshadowa name that hides another (local variables, members)
-Werrorturns warnings into errors, so they cannot be ignored

Key points

  • Compile with -g -O0 to debug; step into virtual calls to see which function really runs.
  • set print object on and info vtbl show an object's dynamic type and its vtable.
  • Run tests under AddressSanitizer; treat warnings as errors.
