Copying and moving

Copying an object duplicates what it owns; moving it transfers ownership and leaves an empty shell. C++ picks between them for you, and knowing its rules avoids both bugs and slow code.

The five special member functions

Besides the destructor, a class has four functions that say what copying and moving mean. The compiler generates all of them when you do not write them, by copying or moving each member in turn:

FunctionRuns forShould
T(const T&) copy constructorT b = a; · pass by valuemake an independent duplicate
T(T&&) move constructorT b = std::move(a); · temporariessteal a's resources, leave a valid but empty
operator=(const T&) copy assignmentb = a;replace b's contents with a duplicate
operator=(T&&) move assignmentb = std::move(a);replace b's contents by stealing
~T() destructorend of lifetimerelease what the object owns

Here is a class whose special members announce themselves. Buffer owns 1000 doubles, so a copy is expensive and a move is nearly free:

// copy_move.cpp -- the five special member functions, each announcing itself
#include <iostream>
#include <string>
#include <utility>
#include <vector>

class Buffer {
public:
    explicit Buffer(std::string name, std::size_t n = 1000) : name_(std::move(name)), data_(n, 0.0) {
        std::cout << "  construct " << name_ << '\n';
    }
    Buffer(const Buffer& o) : name_(o.name_ + "'"), data_(o.data_) {                 // copy: duplicate the data
        std::cout << "  COPY " << o.name_ << " -> " << name_ << " (" << data_.size() << " doubles copied)\n";
    }
    Buffer(Buffer&& o) noexcept : name_(std::move(o.name_)), data_(std::move(o.data_)) {   // move: steal it
        std::cout << "  move " << name_ << " (nothing copied)\n";
        o.name_ = "(moved-from)";
    }
    Buffer& operator=(const Buffer& o) {
        std::cout << "  COPY-assign " << o.name_ << " into " << name_ << '\n';
        data_ = o.data_; return *this;
    }
    Buffer& operator=(Buffer&& o) noexcept {
        std::cout << "  move-assign " << o.name_ << " into " << name_ << '\n';
        data_ = std::move(o.data_); return *this;
    }
    ~Buffer() { std::cout << "  destroy " << name_ << '\n'; }
private:
    std::string name_;
    std::vector<double> data_;
};

Buffer make_buffer() { return Buffer("made"); }   // C++17: returned directly into the caller's variable

int main() {
    std::cout << "1. Buffer b = a;\n";
    { Buffer a("a"); Buffer b = a; }
    std::cout << "2. Buffer b = std::move(a);\n";
    { Buffer a("a"); Buffer b = std::move(a); }
    std::cout << "3. Buffer m = make_buffer();\n";
    { Buffer m = make_buffer(); }
    std::cout << "4. v.push_back(...) three times\n";
    {
        std::vector<Buffer> v;
        v.reserve(3);                      // without reserve, growing the vector would move the old elements too
        v.push_back(Buffer("x"));
        v.emplace_back("y");               // builds in place: no temporary at all
        Buffer z("z");
        v.push_back(z);
    }
}

Step through it

Follow every special member function as it runs. Expand a and b to see the vector being copied, or stolen by a move. The recording was made by stepping through the real program under LLDB; use the buttons, the slider or the arrow keys.

  • Case 2: std::move(a) does not move anything by itself. It is a cast that says "I no longer need a", which lets the move constructor be chosen. Afterwards a still exists (it is destroyed at the brace) but is empty.
  • Case 3: no copy and no move at all. Since C++17, returning a temporary initializes the caller's variable directly: guaranteed copy elision.
  • Case 4: push_back(Buffer("x")) moves the temporary in; emplace_back("y") constructs in place; push_back(z) must copy, because z is still in use.

Mark moves noexcept When a std::vector grows, it must transfer its elements to new memory without risking a half-finished state if an exception is thrown. If your move constructor might throw (is not noexcept), the vector plays it safe and copies every element instead. Moves that only swap pointers cannot throw: say so with noexcept.

The rules of zero, three and five

  • Rule of zero (the goal): build classes from members that already manage themselves (std::string, std::vector, std::unique_ptr) and write none of the five. The generated ones are correct and efficient.
  • Rule of three / five: if a class manages a raw resource and needs a custom destructor, it almost certainly needs custom copy operations too (three), and should have move operations (five). Otherwise the generated copy duplicates a raw pointer and two objects delete the same memory. Exercise 4 in the Practice lesson writes all five.
  • Forbid what makes no sense: = delete the copy operations of unique resources (files, sockets, threads). std::unique_ptr does exactly that:
copy_unique.cpp
#include <memory>
struct Shape { virtual ~Shape() = default; };
int main() {
    auto a = std::make_unique<Shape>();
    auto b = a;            // a unique_ptr has exactly one owner
}
Compiler says
copy_unique.cpp:5:10: error: call to implicitly-deleted copy constructor of 'unique_ptr<Shape>'

Base classes and copying Copying through a base class slices (lesson 05). Polymorphic base classes therefore usually disable copying or make it protected, and offer a virtual clone() instead (lesson 07).

Key points

  • Copy duplicates, move transfers; std::move only marks an object as movable.
  • Returning a local or a temporary by value is cheap: elided or moved.
  • Prefer the rule of zero; when you must write the five, make the moves noexcept.
