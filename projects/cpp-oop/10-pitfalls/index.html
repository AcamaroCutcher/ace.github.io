Four surprises in overriding

pitfalls.cppRun online ↗
// pitfalls.cpp -- four surprises in C++ inheritance, each one demonstrated
#include <iostream>

// 1. A virtual call inside a constructor does not reach the derived class.
struct Widget {
    Widget() { std::cout << "1. constructing: " << kind() << '\n'; }
    virtual ~Widget() = default;
    virtual const char* kind() const { return "Widget"; }
    void show() const { std::cout << "1. afterwards:  " << kind() << '\n'; }
};
struct Button : Widget {
    const char* kind() const override { return "Button"; }
};

// 2. Declaring f(int) in the derived class hides every Base::f, unless you write "using".
struct Base {
    virtual ~Base() = default;
    void f(int) const { std::cout << "Base::f(int)\n"; }
    void f(double) const { std::cout << "Base::f(double)\n"; }
};
struct Hides : Base {
    void f(int) const { std::cout << "Hides::f(int)\n"; }
};
struct Unhides : Base {
    using Base::f;                               // bring Base's overloads back
    void f(int) const { std::cout << "Unhides::f(int)\n"; }
};

// 3. Default arguments come from the static type, even though the function is virtual.
struct Printer {
    virtual ~Printer() = default;
    virtual void print(int n = 1) const { std::cout << "Printer " << n << '\n'; }
};
struct Fancy : Printer {
    void print(int n = 2) const override { std::cout << "Fancy " << n << '\n'; }
};

// 4. A misspelled override silently makes a new function, unless you write "override".
struct Animal {
    virtual ~Animal() = default;
    virtual const char* sound() const { return "..."; }
};
struct Cat : Animal {
    const char* Sound() const { return "meow"; }     // capital S: NOT an override
    // const char* Sound() const override { ... }    // with override this would not compile
};

int main() {
    Button b;
    b.show();

    std::cout << "2. "; Hides{}.f(2.5);              // 2.5 converts to int: Base::f(double) is hidden
    std::cout << "2. "; Unhides{}.f(2.5);

    Fancy fancy;
    const Printer& p = fancy;
    std::cout << "3. "; p.print();                   // Fancy's body with Printer's default argument
    std::cout << "3. "; fancy.print();

    Cat cat;
    const Animal& a = cat;
    std::cout << "4. the cat says " << a.sound() << '\n';
}
Compiler warning
pitfalls.cpp:52:35: warning: implicit conversion from 'double' to 'int' changes value from 2.5 to 2 [-Wliteral-conversion]
Output
1. constructing: Widget
1. afterwards:  Button
2. Hides::f(int)
2. Base::f(double)
3. Fancy 1
3. Fancy 2
4. the cat says ...

Download pitfalls.cpp compiled with -std=c++17 -Wall -Wextra

  1. Virtual calls in constructors and destructors do not reach the derived class: while Widget() runs, the Button part does not exist yet, so the object is still a Widget.
  2. Name hiding: declaring f(int) in Hides hides all of Base's f overloads, so f(2.5) silently converts 2.5 to 2. The compiler warning above is the only hint. using Base::f; brings the overloads back.
  3. Default arguments are static: the body comes from the dynamic type (Fancy), the default argument from the static type (Printer). Do not give overrides different defaults.
  4. A typo creates a new function: Sound is not sound, so the cat says "...". Writing override turns this into a compile error.

Three more

more_pitfalls.cppRun online ↗
// more_pitfalls.cpp -- three more surprises, demonstrated
#include <iostream>
#include <memory>
#include <stdexcept>
#include <string>

// 5. Catching an exception by value slices it: the derived part is lost.
struct AppError : std::runtime_error {
    int code;
    AppError(const std::string& m, int c) : std::runtime_error(m), code(c) {}
};

// 6. A derived member with the same name hides the base member; there are now two.
struct Base { int value = 1; virtual ~Base() = default; };
struct Derived : Base { int value = 2; };

// 7. Copying a class that holds a raw owning pointer copies the pointer, not the object.
struct Holder {
    int* p;
    explicit Holder(int v) : p(new int(v)) {}
    ~Holder() { delete p; }
    // Holder(const Holder&) and operator= are generated: they copy p itself -> two owners, double delete
};
struct SafeHolder {
    std::unique_ptr<int> p;                     // the fix: let a smart pointer own it
    explicit SafeHolder(int v) : p(std::make_unique<int>(v)) {}
    SafeHolder(const SafeHolder& o) : p(std::make_unique<int>(*o.p)) {}   // deep copy, if copying makes sense
};

int main() {
    try { throw AppError("disk full", 28); }
    catch (std::runtime_error e) {             // by value: e is a plain runtime_error copy
        std::cout << "5. caught by value: " << e.what() << ", is it an AppError? "
                  << (dynamic_cast<AppError*>(&e) ? "yes" : "no") << '\n';
    }
    try { throw AppError("disk full", 28); }
    catch (const std::runtime_error& e) {      // by reference: the real object
        auto* app = dynamic_cast<const AppError*>(&e);
        std::cout << "5. caught by reference: is it an AppError? " << (app ? "yes, code " + std::to_string(app->code) : "no") << '\n';
    }

    Derived d;
    Base& b = d;
    std::cout << "6. d.value = " << d.value << ", b.value = " << b.value << ", d.Base::value = " << d.Base::value << '\n';

    SafeHolder s1(7);
    SafeHolder s2 = s1;
    *s2.p = 8;
    std::cout << "7. deep copy: s1 = " << *s1.p << ", s2 = " << *s2.p << '\n';
    // Holder h1(7); Holder h2 = h1;           // compiles, then crashes with a double delete at the end of main
}
Output
5. caught by value: disk full, is it an AppError? no
5. caught by reference: is it an AppError? yes, code 28
6. d.value = 2, b.value = 1, d.Base::value = 1
7. deep copy: s1 = 7, s2 = 8

Download more_pitfalls.cpp compiled with -std=c++17 -Wall -Wextra

  1. Catch exceptions by const&, never by value: a by-value catch copies (slices) the exception into the base type, and the derived information is lost.
  2. A data member with the same name as a base member does not replace it: the object now has both, and which one you see depends on the static type. Give members distinct names.
  3. Owning raw pointers and the generated copy: copying Holder copies the pointer, so two objects delete the same memory. Own through std::unique_ptr and write a deep copy if copying makes sense (lesson 03).

When it crashes: calling a pure virtual function

Pitfall 1 has a nastier form. If a base constructor indirectly calls a pure virtual function, there is no function to run at all: the C++ runtime aborts the program. The compiler does not warn, because the call goes through an ordinary member function.

pure_virtual_call.cppRun online ↗
// pure_virtual_call.cpp -- calling a pure virtual function during construction
// expect: crash
#include <iostream>

class Device {
public:
    Device() { std::cout << "Device(): initializing\n"; init(); }   // calls a virtual function, indirectly
    virtual ~Device() = default;
    void init() { configure(); }               // looks harmless...
    virtual void configure() = 0;              // ...but while Device() runs, the object is only a Device
};

class Camera : public Device {
public:
    void configure() override { std::cout << "Camera::configure\n"; }
};

int main() {
    Camera c;                                   // aborts: there is no Device::configure to call
    std::cout << "never printed\n";
}
Output: the program crashes
Device(): initializing
libc++abi: Pure virtual function called!
[the program stopped: Abort trap: 6 (SIGABRT)]

Download pure_virtual_call.cpp compiled with -std=c++17 -Wall -Wextra

The fix is the same as for pitfall 1: do not call virtual functions during construction or destruction. Use a separate init() called after construction, or a factory function that constructs and then initializes.

Key points

  • Compile with -Wall -Wextra and read the warnings: several of these traps are flagged.
  • Write override; catch by const&; avoid virtual calls in constructors and destructors.
  • Do not reuse names across a hierarchy unless you mean to override a virtual function.
