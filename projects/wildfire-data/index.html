One PostgreSQL database that links every US wildfire to its satellite record: VIIRS and MODIS heat detections, daily perimeters, LiDAR from before and after the burn, burn-severity imagery, fuels and weather. Built so a spread model can ask for a fire and get back everything it needs to learn from.

Why build another wildfire database?

Machine-learning wildfire datasets exist, but each one covers a slice. None of them puts sub-daily fire spread, the 3D structure of the forest before and after, and burn severity for the same fire into one place you can query.

The design goal is simple to state: ask for a fire, get everything. Its incident record, every perimeter ever mapped, every satellite detection that belongs to it (and how sure we are that it does), the LiDAR and imagery from before and after, the fuels and terrain under it, and the weather over it. From there a training example is one SQL query away.

What changed from the first version. The earlier attempt stored hotspots with no link to any fire, mixed MODIS percentages with VIIRS letter grades in one "confidence" column, threw away the perimeter shapes, kept times as text and cause codes as bare numbers. All five are fixed here, and the 20 questions from the original project proposal are now the database's acceptance test (section 06).

B02SatellitesEvery source
that sees fire

The satellites that watch wildfires

Fire is seen in three ways from above: heat (thermal infrared detections, minutes to hours old), change (optical imagery before and after: burn severity) and structure (LiDAR: the 3D forest that burned). The database keeps all three.

Resolution against revisit

Each dot is a source. Smaller pixels see smaller fires; shorter revisit catches the spread between passes. No single source wins both, which is why they are combined. Click a dot.

A real day of overpasses: Oregon, Labor Day 2020

Every fire detection over Oregon from 7 to 10 September 2020, grouped into 10-minute bins, straight from this database. Polar-orbiting satellites (VIIRS, MODIS) see the state in two windows a day, around 2 a.m. and 1 p.m. local time. The 8–10 hour gaps between them are exactly where geostationary GOES (every 5 minutes, but 2 km pixels) and the new FireSat constellation come in.

The thermal sources in detail

Two changes in 2026 that matter. NOAA ended Suomi-NPP products on 2 November 2026, so live VIIRS now comes from NOAA-20 and NOAA-21 only (the S-NPP archive back to 2012 stays). And FireSat's first three operational satellites reached orbit on 7 July 2026: its data goes to early-adopter agencies first, with non-commercial licences for academic users planned for 2027. The database already has a sensor row and an ingest adapter waiting for it.

The schema: one fire, everything attached

fire_event sits in the middle. Everything else hangs off it by key or by space and time: perimeters over time, detections through an explicit link table, imagery, LiDAR, rasters and weather.

Click a table to see its columns and why it is shaped that way. Lines are foreign keys; the dashed line is the spatial–temporal link built by the linking query.

Select a table.

Design rules

  • Space is geometry, time is timestamptz. Points, footprints and perimeters are PostGIS geometries in WGS 84; areas and distances use the geography type (metres, on the ellipsoid). Every time is UTC.
  • Never invent a number. MODIS confidence is a percentage, VIIRS confidence is low/nominal/high. Each keeps its own form; a shared three-class column makes them comparable without pretending VIIRS has a percentage.
  • Codes carry their meaning. Cause, incident-type and fuel codes are loaded with their descriptions from NIFC's own definitions.
  • Big files stay outside. LiDAR point clouds and image rasters stay in cloud storage (COG, EPT/COPC); the database stores where they are, when they were taken and how they relate to the fire.
  • Detections are partitioned by month, with spatial (GiST) and time (BRIN) indexes, so one fire's detections come back in milliseconds out of millions.
B04LinkingWhich fire is
this pixel?

Linking a detection to its fire

A satellite reports a hot pixel, not a fire name. The linking query decides which fire each detection belongs to, using where it is and when it was seen, and records how it decided, as a score.

Try it: drag the detection around the fire, and slide the time it was seen. The score below is computed with the same rules the database uses.

ScoreRuleWhy
1.0Inside a perimeter of the fire mapped within ±12 hSame place, same time: no doubt
0.8Inside the fire's final perimeter, during the fireThe fire burned there, at some point
≤ 0.6Within 2 km of the perimeter (or the point of origin), decaying with distancePixels are 375 m–1 km wide and perimeters are drawn by hand
0.4Left over, but part of a cluster within 5 km of a reported originSmall fires that never got a perimeter

"During the fire" means from one day before discovery to three days after the first known end (out, controlled, contained or last mapped perimeter). Detections that FIRMS flags as volcanoes, gas flares or offshore sources are never linked. Each detection gets at most one fire: highest score first, then nearest, then closest in time.

Perimeters can have more than 100,000 vertices, so the query first cuts each one into pieces of at most 64 vertices (ST_Subdivide) and lets the spatial index pair every detection only with nearby pieces. That took the busiest month on record, September 2020, from over ten minutes to under three.

B05ModelsDNN · GNN ·
neural ODE

From database to model

Every moment the fire's state is known, a mapped perimeter or a satellite overpass, becomes a time stamp. Consecutive time stamps make a training pair: the state at t and everything around it are the input; the state at the next time is the label.

Irregular time is a feature. Overpasses come at 1:30 and 13:30, perimeters whenever a crew or aircraft maps one. Fixed-step models resample onto a grid; a neural ODE takes the true time gaps (dt_hours) directly, which is why the training view keeps them.

B08HostingLocal master,
cloud copy

Where the database lives

The full archive is a few gigabytes, more than free cloud tiers hold. So the complete database runs locally for training, and a slimmer copy serves the web app.

Local masterPostgreSQL 17 + PostGIS 3.5 in Postgres.app on a Mac (or the postgis/postgis Docker image). Holds everything; ML exports read from here.
Supabase serving copyPostgres + PostGIS with an automatic REST API. Recent years and the case fires, simplified shapes, read-only access. Free tier 500 MB; Pro plan if it grows.
Cloudflare WorkerA small edge function: proxies NASA FIRMS (which blocks browser requests and needs a private key), caches Supabase answers, converts GOES files to GeoJSON.
GitHub PagesThis page and the app: static files that call the Worker and public open-data services directly.

Run it yourself

# 1. database (PostgreSQL 16+ with PostGIS)
createdb wildfire
for f in schema/*.sql; do psql -d wildfire -f "$f"; done

# 2. data
cd ingest
python reference.py                      # states, counties, NIFC code lists
python nifc.py incidents --csv inform_fire_occurrence_data.csv
python nifc.py perimeters                # WFIGS final + daily perimeters
python firms.py files fire_archive_*.csv # or: firms.py api --source VIIRS_NOAA21_NRT
python lidar.py index && python lidar.py link

# 3. link detections to fires, then test
link/run_link.sh 2020-01 2025-12
pytest tests -q
