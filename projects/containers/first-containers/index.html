Your first containers

The everyday commands: running containers interactively and in the background, ports, environment variables, volumes and bind mounts, and cleaning up.

Run a container and look around

Start an interactive Ubuntu shell. -it connects your keyboard and terminal to it, and --rm deletes the container when you leave:

Terminalshell
docker run -it --rm ubuntu:24.04 bash

You are now root inside a minimal Ubuntu, even if your computer is a Mac. Try a few things:

Inside the containershell
cat /etc/os-release           # Ubuntu 24.04, whatever your own system isps aux                        # only bash and ps: the container sees its own processesapt-get update && apt-get install -y curlcurl -sI https://example.com  # it has network accessexit                          # leaving the shell ends the container

Run the same command again and curl is gone: every container starts fresh from the image. That is a feature. You can break anything inside, and nothing outside is touched.

Long-running containers

Servers run in the background. -d (detached) starts the container and gives you your prompt back; --name gives it a name to use instead of its ID:

Terminalshell
docker run -d --name web -p 8080:80 nginx:1.27-alpinedocker ps                     # running containers (add -a to include stopped ones)docker logs -f web            # follow its output; Ctrl-C stops following, not the container

Open http://localhost:8080 and nginx's welcome page appears: a web server you never installed. Reload a few times and watch the log lines. Then:

Terminalshell
docker exec -it web sh        # open a second shell inside the running containerdocker stop web               # stop it (its files are kept)docker start web              # start it againdocker rm -f web              # stop and delete it
CommandWhat it does
docker run IMAGE [CMD]Create and start a new container (downloads the image if needed)

Practice them here before you touch a real terminal. The simulator follows Docker's real rules: two containers can't share a host port, a running container can't be removed without -f, and an image with nothing to do exits at once.

Publishing ports

A container has its own network, so a server inside it is unreachable until you publish a port: -p HOST:CONTAINER. -p 8080:80 means “connections to port 8080 on my computer go to port 80 in the container”. Two containers can both listen on port 80 inside; they just need different host ports:

Terminalshell
docker run -d --name a -p 8081:80 nginx:1.27-alpinedocker run -d --name b -p 8082:80 nginx:1.27-alpinedocker rm -f a b
Who can connect? -p 8080:80 listens on every network interface, so other machines on the same Wi-Fi can reach it, and on a Linux server Docker's port rules go around the ufw firewall. For anything private, add the address: -p 127.0.0.1:8080:80.

Keeping data: volumes and bind mounts

Anything written inside a container disappears when the container is deleted. Two ways to keep it:

  • A bind mount shows a folder of your computer inside the container: -v /path/on/host:/path/in/container. Best for your own files, such as code, data and documents.
  • A named volume is storage that Docker manages: -v name:/path/in/container. Best for a program's own data, such as a database.
Bind mount: serve the current folder as a websiteshell
mkdir -p ~/site && cd ~/siteecho '<h1>Hello from my folder</h1>' > index.htmldocker run --rm -p 8080:80 -v "$PWD":/usr/share/nginx/html:ro nginx:1.27-alpine# edit index.html, reload the browser: the change shows at once. Ctrl-C to stop.

:ro makes the mount read-only, so the container can read your files but can't change them. Use it whenever the container only needs to read.

Named volume: data that outlives the containershell
docker volume create notesdocker run --rm -v notes:/data alpine sh -c 'date >> /data/log.txt; cat /data/log.txt'docker run --rm -v notes:/data alpine sh -c 'date >> /data/log.txt; cat /data/log.txt'   # two lines nowdocker volume lsdocker volume rm notes

Passing settings

Containerized programs are configured with environment variables, given with -e or collected in a file with --env-file. Each image's page on Docker Hub lists the variables it understands. The official Postgres image, for example, refuses to start without a password:

Terminalshell
docker run -d --name pg -e POSTGRES_PASSWORD=secret -p 127.0.0.1:5432:5432 -v pgdata:/var/lib/postgresql/data postgres:17docker exec -it pg psql -U postgres -c 'select version();'docker rm -f pg               # the data stays in the pgdata volume for next time

-e NAME without =value copies the variable from your own shell, which keeps secrets such as API keys out of your shell history (lesson 06 uses this).

Cleaning up

Images and stopped containers pile up. See how much space Docker uses and reclaim it:

Terminalshell
docker system df              # space used by images, containers, volumes, build cachedocker container prune        # delete all stopped containersdocker image prune -a         # delete images no container usesdocker system prune           # all of the above except volumes

Volumes are never removed by these commands unless you add --volumes, because they hold data.

Exercises

  1. Run python:3.13 interactively (docker run -it --rm python:3.13) and you get a Python prompt. Then run python:3.9 the same way. Two Python versions, nothing installed.
  2. Start nginx in the background, then use docker exec to edit /usr/share/nginx/html/index.html inside it (vi is available). Reload the page. Delete and recreate the container: what happened to your edit, and why?
  3. Repeat exercise 2 with a bind mount instead, so the edit survives.
  4. Run docker run --rm --memory 64m alpine sh -c 'cat /sys/fs/cgroup/memory.max'. That number is the cgroup limit from lesson 01, seen from inside.
