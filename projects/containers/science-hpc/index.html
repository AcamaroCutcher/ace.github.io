Jupyter in one command

The Jupyter project publishes ready-made notebook images with the scientific stack already installed:

Terminal (in your project folder)shell
docker run --rm -p 127.0.0.1:8888:8888 -v "$PWD":/home/jovyan/work quay.io/jupyter/scipy-notebook# open the http://127.0.0.1:8888/lab?token=… link it prints

Your folder appears as work/ in JupyterLab. Other images in the family: datascience-notebook (Python, R and Julia), pytorch-notebook and tensorflow-notebook. To add packages permanently, build on top of one:

DockerfileDockerfile
# for a paper, pin a dated tag listed on quay.io/repository/jupyter/scipy-notebookFROM quay.io/jupyter/scipy-notebookRUN pip install --no-cache-dir xarray netCDF4 cartopy

Reproducible research environments

A paper's results depend on its software versions. A container records them in a form anyone can run years later. To make it truly reproducible:

  • Pin everything. A base image tag, exact package versions (pip freeze > requirements.txt), and ideally the image's digest, a hash that never changes even if a tag is moved:
Terminalshell
docker pull python:3.13-slimdocker inspect --format '{{index .RepoDigests 0}}' python:3.13-slim# python@sha256:4c2f…  → use it as:  FROM python:3.13-slim@sha256:4c2f…
  • Publish the image with the code: push it to a registry, and for long-term archiving save it to a file and deposit it with the data (Zenodo, OSF, a university repository):
Terminalshell
docker save my-analysis:paper-v1 | gzip > my-analysis-paper-v1.tar.gzdocker load < my-analysis-paper-v1.tar.gz            # years later, on any machine with Docker
  • Keep the Dockerfile in the repository, so readers can see how the environment was made, and not only download it.

Why clusters don't run Docker

Supercomputers and university clusters almost never allow Docker: its daemon runs as root, and any user who can start containers could become root on a shared machine. Clusters use Apptainer instead (formerly called Singularity; many sites still have the singularity command). It was designed for HPC:

  • it runs as you, with no daemon and no root;
  • an image is a single .sif file you can copy, share and keep next to your data;
  • your home directory and current folder are visible inside by default, and the cluster's file systems, GPUs and fast network work as usual;
  • it runs Docker images directly, so the images from the earlier lessons go with you.

Some sites also offer Podman, Charliecloud, Enroot or Sarus. Check your cluster's documentation; the ideas are the same.

Apptainer in practice

On the clustershell
module load apptainer                                 # or: module load singularityapptainer pull docker://python:3.13-slim              # makes python_3.13-slim.sifapptainer exec python_3.13-slim.sif python --versionapptainer shell python_3.13-slim.sif                  # an interactive shell insideapptainer run docker://ghcr.io/USERNAME/my-analysis:1.0   # pull and run your own image

Apptainer can also build from its own recipe format, a definition file:

code/apptainer/science.defshell
# Apptainer definition file (lesson 07). Build: apptainer build science.sif science.defBootstrap: dockerFrom: python:3.13-slim %post    pip install --no-cache-dir numpy scipy matplotlib xarray netCDF4 %runscript    exec python "$@" %labels    Description Python with the scientific stack, for cluster jobs

Download science.def

Terminalshell
apptainer build science.sif science.def               # some clusters need --fakeroot, or a build node

The easiest workflow is often: build a Docker image on your laptop, push it to a registry, and apptainer pull docker://… it on the cluster.

CPU type Almost all clusters are x86_64 (amd64). A Mac with Apple silicon builds arm64 images by default, and those fail on the cluster with exec format error. Build with docker buildx build --platform linux/amd64 … (lesson 03).

Containers in Slurm jobs

A container is just a command in a job script, so nothing changes about how you submit:

code/apptainer/job.slurmshell
#!/bin/bash# Run a containerized analysis on a Slurm cluster (lesson 07). Submit: sbatch job.slurm#SBATCH --job-name=container-job#SBATCH --ntasks=1#SBATCH --cpus-per-task=4#SBATCH --mem=8G#SBATCH --time=00:30:00 module load apptainer        # the module name differs between clusters (sometimes "singularity") # your home directory and the current folder are visible inside the container by default;# --bind adds other folders, such as a scratch file systemapptainer exec --bind /scratch science.sif python analysis.py

Download job.slurm

Terminalshell
sbatch job.slurmsqueue -u "$USER"

GPUs and MPI

GPUs: add --nv (NVIDIA) or --rocm (AMD), and the host's driver is made available inside: apptainer exec --nv pytorch.sif python train.py. The CUDA toolkit comes from the image, the driver from the cluster.

MPI: the usual approach is the hybrid model. The cluster's launcher starts one container per rank, and the MPI library inside the container talks to the one on the host:

In a job scriptshell
srun apptainer exec model.sif ./model.exe

For this to work, the MPI inside the image must be compatible with the cluster's (the same implementation, such as Open MPI or MPICH, and a similar version). A common trick is to build the image with the same MPI version the cluster provides, or to bind the host's MPI into the container. Big Fortran models with long dependency lists, such as WRF or FIRETEC from the Fortran for FIRETEC course, are good candidates: build the environment once, then run it on any cluster.
