One pattern for any tool

Almost every “run a program on my files” task uses the same shape:

The patternshell
docker run --rm -it -v "$PWD":/work -w /work IMAGE COMMAND ARGS
PartWhy
--rmThrow the container away afterwards. The image stays, so the next run starts at once.
-itInteractive with a terminal, for tools that ask questions or print colors. Leave it out in scripts.
-v "$PWD":/workYour current folder appears as /work inside, so the tool can read and write your files.
-w /workStart the command in that folder, so relative file names just work.

Wrap it in a shell function and a containerized tool feels installed. Add to ~/.zshrc or ~/.bashrc:

~/.zshrcshell
# drun IMAGE [COMMAND...]: run a container on the current folderdrun() { docker run --rm -it -v "$PWD":/work -w /work "$@"; }
File ownership on Linux Many images run as root, so on a Linux host the files they create in your folder belong to root. Add --user "$(id -u):$(id -g)" to run as yourself. Docker Desktop on a Mac or Windows translates ownership for you.

Examples

Python, any version

Terminalshell
drun python:3.13 python analysis.pydrun python:3.9 python old_script.py                     # an old project, without touching your own Pythondrun python:3.13 sh -c "pip install pandas && python analysis.py"   # quick one-off with a package

If you install the same packages every time, that's the moment to write a three-line Dockerfile (lesson 03) instead.

Documents with pandoc and LaTeX

Terminalshell
docker run --rm -v "$PWD":/data pandoc/latex report.md -o report.pdf

The pandoc/latex image already sets /data as its folder and pandoc as its entrypoint, so the arguments go straight to pandoc. A full LaTeX installation is several gigabytes; this way it is one download you can delete later.

Compilers: Fortran, C, C++

Terminalshell
drun gcc:14 gfortran -O2 -o hello hello.f90drun gcc:14 ./hello

The program is a Linux program, so on a Mac it runs inside the container (second line) but not directly in your terminal. That is exactly what you want when the code is headed for a Linux cluster.

Databases for development

Databases are the classic case: no installer, no background service left running, a fresh copy whenever you want one, and several versions side by side.

Terminalshell
# PostgreSQL, with its data in a volumedocker run -d --name pg -e POSTGRES_PASSWORD=dev -p 127.0.0.1:5432:5432 -v pgdata:/var/lib/postgresql/data postgres:17docker exec -it pg psql -U postgres # Redis, MySQL and MongoDB follow the same patterndocker run -d --name redis -p 127.0.0.1:6379:6379 redis:7docker run -d --name mysql -e MYSQL_ROOT_PASSWORD=dev -p 127.0.0.1:3306:3306 -v mysqldata:/var/lib/mysql mysql:8.4docker run -d --name mongo -p 127.0.0.1:27017:27017 -v mongodata:/data/db mongo:8

Programs on your computer connect to localhost on the published port, as if the database were installed normally.

Self-hosted applications

Many complete applications are published as images, which is how people run them on a home server, a NAS or a Raspberry Pi. Each project's documentation gives its docker run or Compose file; usually it's a port, a volume or two, and some settings.

ApplicationWhat it isImage
NextcloudYour own Dropbox / Google Drivenextcloud
JellyfinMedia server for your films and musicjellyfin/jellyfin
Home AssistantHome automationghcr.io/home-assistant/home-assistant
GiteaA self-hosted GitHubgitea/gitea
VaultwardenPassword manager server (Bitwarden-compatible)vaultwarden/server
Uptime KumaWatches your websites and alerts you when one is downlouislam/uptime-kuma
Example: Uptime Kumashell
docker run -d --name kuma --restart unless-stopped -p 127.0.0.1:3001:3001 -v kuma:/app/data louislam/uptime-kuma:1# http://localhost:3001

--restart unless-stopped brings the container back after a crash or a reboot, which is what you want for anything that should always be on.

Desktop programs Containers are made for programs without windows. Some publishers, such as linuxserver.io, package Linux desktop apps with a built-in web desktop so you use them in a browser tab. Mac and Windows programs can't run in a Linux container at all.

Choosing images you can trust

An image is software from a stranger, with the same risks as any download. Prefer, in order:

  1. Docker Official Images (no slash in the name: python, postgres, nginx), maintained with the upstream projects.
  2. Images published by the project itself (pandoc/latex, rocker/…, ghcr.io/home-assistant/…), linked from its own website or GitHub.
  3. Verified Publisher and actively updated images. Check the date of the last push and the source repository.

Pin a version tag (postgres:17, not postgres) so an update never surprises you, and read the Dockerfile when one is linked.
