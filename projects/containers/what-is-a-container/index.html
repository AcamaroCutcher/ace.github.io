The problem containers solve

Every program depends on other things: a particular Python version, a C library, a database driver, a config file in a particular place. The classic failure is “it works on my machine”: the code is fine, but the machine it lands on has different versions of those things.

A container packs a program together with everything it needs to run, its own files, libraries and settings, into one unit that runs the same way on a laptop, a lab server, a cloud machine or a supercomputer. The name comes from shipping containers: a standard box that every crane, ship and truck can handle without knowing what is inside.

In one sentence A container is a program running in a sealed-off view of the computer, with its own files, network and process list, built from a read-only template called an image.

Containers versus virtual machines

A virtual machine (VirtualBox, Parallels, a cloud server) emulates a whole computer and boots a full operating system inside it. A container doesn't: it is an ordinary process on the host, which the Linux kernel walls off so that it can only see its own files and its own network. That's why containers start in well under a second and weigh megabytes instead of gigabytes, and why one laptop can run dozens of them.

The trade-off is isolation. Containers share the host's kernel, so a VM is a stronger wall between programs you don't trust. Containers also only run programs built for the kernel they share: Docker containers are Linux programs. (On a Mac or Windows PC, Docker quietly runs one small Linux VM and puts all your containers in it.)

Docker is the best-known tool, but the image format is an open standard (OCI). The same images run in Podman, in Apptainer on clusters, in Kubernetes, and on cloud services, so what you learn here carries over.

What happens under the hood

A container is not a special kind of object in Linux. It is a normal process that the kernel has been asked to limit in three ways:

  • Namespaces decide what the process can see: its own process list (it believes it is process 1), its own network interfaces and ports, its own host name, and its own root file system.
  • Control groups (cgroups) decide how much it can use: memory, CPU time, number of processes.
  • A layered file system (overlayfs) stacks the image's read-only layers and puts one writable layer on top, so a hundred containers from the same image share one copy on disk.

Docker itself is a background service (the daemon) plus the docker command you type. The command asks the daemon to download images, set up those namespaces and cgroups, and start your process.

Installing Docker

macOS and Windows

Install Docker Desktop, open it once, and wait for the whale icon to say it is running. On Windows it uses WSL 2, which the installer sets up. Docker Desktop is free for personal use, education, open-source work and small businesses; large companies need a paid plan. Free alternatives on a Mac are OrbStack (free for personal use), Colima and Podman; all of them accept the same docker commands used in this course.

Linux

Install Docker Engine from your distribution's instructions on docs.docker.com, or with Docker's convenience script:

Linuxshell
curl -fsSL https://get.docker.com | shsudo usermod -aG docker "$USER"     # use docker without sudo (log out and in again)
About the docker group Membership in the docker group is effectively root access to the machine, because Docker can mount any folder into a container. Only add trusted users. Rootless Docker and Podman avoid this.

Check that it works

Terminalshell
docker --versiondocker run hello-world

The second command downloads a tiny image from Docker Hub, starts a container that prints a greeting explaining what just happened, and exits. If you see “Hello from Docker!”, you're ready for lesson 02.

Apple silicon and Intel Images are built for a CPU type. Most popular images include both arm64 (Apple silicon, Raspberry Pi, many cloud servers) and amd64 (Intel and AMD). If an image only exists for amd64, Docker on a Mac can still run it with --platform linux/amd64 through emulation, only more slowly. Lesson 07 explains why this matters when you take images to a cluster.
