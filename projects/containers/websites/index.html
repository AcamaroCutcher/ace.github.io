Do you need a container at all? A purely static site can go straight to GitHub Pages, Netlify or Cloudflare Pages for free, with no server to look after. That is how acamaro.com is hosted. Containers earn their keep once there is a program running on the server: an API, a database, a login.

Development servers without installing Node

JavaScript projects (React, Vue, Svelte, Astro) need Node.js and hundreds of packages. Run them in a container with your project folder mounted:

Terminal (in a Vite project)shell
docker run --rm -it -p 5173:5173 -v "$PWD":/app -w /app node:22 sh -c "npm install && npm run dev -- --host 0.0.0.0"
The most common container mistake Development servers listen on localhost by default. Inside a container, localhost means the container itself, so the published port leads nowhere and the browser says the connection was reset. Tell the server to listen on 0.0.0.0 (all interfaces): --host 0.0.0.0 for Vite, flask run --host 0.0.0.0, python -m http.server --bind 0.0.0.0.

Docker Compose: several containers as one app

Real web apps are several programs: the app, a database, maybe a cache and a web server in front. Typing a long docker run for each gets old fast. Compose describes them all in one compose.yaml and manages them together:

CommandWhat it does
docker compose up -d --buildBuild what needs building, create the network and volumes, start everything in the background
docker compose ps / logs -f webStatus of the services / follow one service's output
docker compose exec db psql -U appRun a command in a running service
docker compose downStop and remove the containers and network (volumes are kept)
docker compose down -vThe same, and delete the volumes with all their data

Compose puts all the services on a private network where each one can reach the others by service name: the app connects to the database at the host name db.

A complete app: Flask, PostgreSQL and HTTPS

The app counts visits in a PostgreSQL table:

code/web-stack/app/app.pyPython
"""Visit counter: Flask + PostgreSQL, run together with Docker Compose (lesson 05)."""import os import psycopgfrom flask import Flask app = Flask(__name__)DSN = os.environ["DATABASE_URL"]  # postgresql://app:PASSWORD@db:5432/app ("db" is the service name)  def connect():    return psycopg.connect(DSN, autocommit=True)  # runs once at start-up (gunicorn --preload imports this file once, before forking workers)with connect() as conn:    conn.execute("CREATE TABLE IF NOT EXISTS visits (id serial PRIMARY KEY, at timestamptz DEFAULT now())")  @app.get("/")def home():    with connect() as conn:        conn.execute("INSERT INTO visits DEFAULT VALUES")        (count,) = conn.execute("SELECT count(*) FROM visits").fetchone()    return f"<h1>Hello!</h1><p>This page has been visited {count} times.</p>"  @app.get("/health")def health():    return {"ok": True}

Terminal (in web-stack/)shell
cp .env.example .env               # then edit the passworddocker compose up -d --builddocker compose ps                  # all three running, db "healthy"# open https://localhost, accept the local certificate warning once, and reload a few timesdocker compose logs -f webdocker compose down                # the visit count is still in the db-data volume next time

Note what's not there: no ports on web or db. Only Caddy is reachable from outside, which is exactly the shape you want on a real server. depends_on with condition: service_healthy makes the app wait until Postgres answers its health check, so the app doesn't crash on start-up.

Putting it on the internet

The image you tested is the thing you deploy, which is the whole point. Three common routes:

RouteHowGood for
Your own server (VPS)Rent a small Linux server (Hetzner, DigitalOcean, Linode, AWS Lightsail…), install Docker, copy the project, set SITE_ADDRESS to your domain, point the domain's DNS A record at the server, open ports 80 and 443, and run docker compose up -d. Caddy fetches the certificate.Full control, fixed low monthly price, several apps on one machine
A container platformPush the image to a registry and give it to Google Cloud Run, Fly.io, Render, Railway, Azure Container Apps or AWS ECS. They run it, add HTTPS, and scale it, often down to zero when idle. The database is usually their managed one.No server upkeep; pay for what you use
KubernetesAn orchestrator that runs containers across many machines with rolling updates and self-healing.Large systems and teams. Not the place to start

On a server you can either build there (docker compose up -d --build after copying or git pull-ing the code) or build on your computer, push to a registry, and replace build: with image: ghcr.io/USERNAME/app:1.0. Remember to build for linux/amd64 if your Mac is Apple silicon and the server is not.

Updates and backups

Terminal (on the server)shell
docker compose pull                # newer versions of the images you usedocker compose up -d --build       # recreate only what changeddocker image prune -f              # remove the old images # back up and restore the databasedocker compose exec -T db pg_dump -U app app > backup-$(date +%F).sqldocker compose exec -T db psql -U app app < backup-2026-11-11.sql

A volume is just data on that one machine, so copy backups somewhere else. A pg_dump file is the safest format to keep.

Exercises

  1. Run the stack and visit the page ten times. Run docker compose down and up -d again: is the count kept? Now try down -v.
  2. Run docker compose exec db psql -U app -c 'select * from visits;' and look at the timestamps.
  3. Add a Redis service to compose.yaml and reach it from the web container with docker compose exec web python -c "import socket; print(socket.gethostbyname('redis'))".
  4. Add a /stats route to app.py that returns the number of visits per day, then rebuild just that service with docker compose up -d --build web. The database keeps running.
