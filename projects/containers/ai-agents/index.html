Why AI and containers go together

  • Dependencies. Machine-learning stacks pin exact versions of Python, PyTorch, CUDA and drivers. An image freezes a combination that works.
  • Serving. Model servers (Ollama, vLLM, text-generation-inference) and chat front ends are distributed as images.
  • Containment. An agent is a program that decides for itself which commands to run and which files to read or change. A container limits what it can reach, so a mistake stays inside the box.

Run open models privately: Ollama and Open WebUI

Ollama downloads and runs open-weight models (Llama, Qwen, Gemma, Mistral and many more), and Open WebUI gives them a ChatGPT-style interface. Nothing leaves your computer.

On a Mac, models in Docker run on the CPU Docker's Linux VM can't use the Apple GPU, so large models are slow there. For speed, install the Ollama app natively (it uses the GPU through Metal) and keep only Open WebUI in a container, pointed at the host with OLLAMA_BASE_URL: http://host.docker.internal:11434. Docker Desktop's Model Runner (docker model run …) also runs models natively on Apple silicon. On Linux and Windows with an NVIDIA card, the container gets the GPU (next section).

GPUs in containers

On a Linux machine with an NVIDIA GPU, install the driver on the host and the NVIDIA Container Toolkit. Then --gpus all hands the GPU to a container; the CUDA libraries come from the image, so different projects can use different CUDA versions:

Terminal (Linux + NVIDIA)shell
docker run --rm --gpus all nvidia/cuda:12.6.3-base-ubuntu24.04 nvidia-smidocker run --rm -it --gpus all -v "$PWD":/work -w /work pytorch/pytorch python train.py

In Compose, uncomment the deploy: block in the Ollama file above. Windows with Docker Desktop and WSL 2 supports --gpus all too. On clusters, Apptainer uses --nv (lesson 07).

Your own agent, in a box

An agent is a loop: the model reads the task, asks to use a tool, your code runs the tool and sends back the result, and so on until the model has an answer. This one uses Claude through the official anthropic Python SDK, whose tool runner does the loop for you. Its two tools can list and read files under /workspace and nothing else, and the container makes that a hard limit: the only files it can ever see are the ones you mount.

code/agent/agent.pyPython
"""A small Claude agent that can read (but not change) the files in /workspace (lesson 06). Run it in a container: the only files it can ever see are the ones you mount there.Usage: python agent.py "your question about the files""""import sysfrom pathlib import Path import anthropicfrom anthropic import beta_tool WORKSPACE = Path("/workspace")client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment  def inside_workspace(path: str) -> Path:    p = (WORKSPACE / path).resolve()    if p != WORKSPACE and WORKSPACE not in p.parents:        raise ValueError(f"{path} is outside /workspace")    return p  @beta_tooldef list_files(directory: str = ".") -> str:    """List the files and folders in a directory of the workspace.     Args:        directory: Path relative to the workspace root, e.g. "." or "src".    """    d = inside_workspace(directory)    names = [p.name + ("/" if p.is_dir() else "") for p in sorted(d.iterdir())]    return "\n".join(names) or "(empty)"  @beta_tooldef read_file(path: str) -> str:    """Read a text file from the workspace (at most the first 20,000 characters).     Args:        path: Path relative to the workspace root, e.g. "README.md".    """    return inside_workspace(path).read_text(errors="replace")[:20_000]  question = " ".join(sys.argv[1:]) or "What is in this folder? Summarize it in a few sentences." runner = client.beta.messages.tool_runner(    model="claude-opus-5-5",    max_tokens=16000,    betas=["server-side-fallback-2026-07-01"],    fallbacks="default",  # if a request is declined, the API retries it on a fallback model    system="You answer questions about the files in /workspace. Look at the files with your tools before answering.",    tools=[list_files, read_file],    messages=[{"role": "user", "content": question}],) last = Nonefor message in runner:  # one message per turn; the runner calls the tools in between    last = message    for block in message.content:        if block.type == "tool_use":            print(f"  [tool] {block.name} {block.input}", file=sys.stderr)        elif block.type == "text":            print(block.text) if last is not None and last.stop_reason == "refusal":    print("The model declined this request.", file=sys.stderr)

Three layers of protection are stacked here: the tools only read, the path check refuses anything outside /workspace, and even if both failed, the mount is read-only (:ro) and the rest of your disk doesn't exist inside the container. -e ANTHROPIC_API_KEY with no value passes your key in at run time, so it never ends up in the image. To let an agent write, mount a copy or a Git working tree you can reset, not your only copy.

About the code It uses Claude Opus 5.5 (claude-opus-5-5) and the SDK's @beta_tool decorator, which builds each tool's description from the function's signature and docstring. fallbacks="default" lets the API retry a declined request on a fallback model. The tool loop was tested against the anthropic 2.8 SDK with a mock server; see platform.claude.com/docs for the current API.

Sandboxing a coding agent

Coding agents such as Claude Code run shell commands, install packages and edit files. On your own computer they ask permission for risky steps. Inside a container you can give them more freedom, because what they can touch is limited to the project folder you mount. A dev container is a standard way to describe such an environment; VS Code, Cursor, JetBrains IDEs and GitHub Codespaces open it with one click.

code/devcontainer/DockerfileDockerfile
# A sandbox for a coding agent: Claude Code in a container (lesson 06)FROM node:22-slim RUN apt-get update \ && apt-get install -y --no-install-recommends git ca-certificates ripgrep python3 \ && rm -rf /var/lib/apt/lists/* RUN npm install -g @anthropic-ai/claude-code # a folder for Claude Code's settings and login, owned by the ordinary "node" userRUN mkdir -p /home/node/.claude && chown node:node /home/node/.claude USER nodeWORKDIR /workspaceCMD ["claude"]

Download devcontainer.json

Put both files in a .devcontainer/ folder in your project and run Dev Containers: Reopen in Container in VS Code (it needs the Dev Containers extension). Or use plain Docker:

Terminal (in your project)shell
docker build -t claude-sandbox .devcontainerdocker run --rm -it -v "$PWD":/workspace -v claude-config:/home/node/.claude claude-sandbox# first run: log in when Claude Code asks, or add -e ANTHROPIC_API_KEY to use an API key

The claude-config volume keeps your login and settings between runs. What this sandbox does and doesn't protect:

ProtectedNot protected
Everything on your computer outside the project folder: other projects, SSH keys, browser data, documentsThe project folder itself: it is mounted read-write. Commit to Git first so you can review and undo
Your installed software: whatever the agent installs lives and dies in the containerThe network: the agent can still reach the internet, and anything it can read it could send

For unattended runs (Claude Code's --dangerously-skip-permissions mode), Anthropic's reference dev container adds a firewall that only allows the few sites the agent needs. Use that, not the minimal one above, and never mount credentials you aren't willing to expose. Claude Code also has a built-in sandbox mode; see its documentation.

Tools for agents: MCP servers in containers

The Model Context Protocol (MCP) is a standard way to give an AI app new tools: a web fetcher, a database, GitHub, a browser. Many MCP servers are published as images (Docker Hub's mcp/ namespace), so you don't install their dependencies, and each one runs walled off from the rest. An MCP client starts the container and talks to it over standard input and output, which is why -i is needed:

Terminalshell
claude mcp add fetch -- docker run -i --rm mcp/fetch

The same command line works in any MCP client's configuration. Docker Desktop's MCP Toolkit manages a catalog of these servers for you.

Running code an AI wrote

If your own agent writes and runs code (data analysis, plotting, tests), run each piece in a disposable container with the doors shut:

A locked-down runshell
docker run --rm --network none --memory 512m --cpus 1 --pids-limit 128 \  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges \  -v "$PWD/job":/job:ro python:3.13-slim python /job/script.py
OptionEffect
--network noneNo network at all: nothing can be downloaded or sent
--memory, --cpus, --pids-limitAn endless loop or a fork bomb can't take down the machine
--read-only --tmpfs /tmpThe file system is read-only except a scratch /tmp in memory
--cap-drop ALL, no-new-privilegesRemoves the special powers even root inside the container normally has

Wrap that in your agent's “run code” tool, with a timeout, and return the output to the model. For code from people or models you truly don't trust, use a stronger sandbox: gVisor (--runtime=runsc), a micro-VM such as Firecracker, or a hosted sandbox such as Anthropic's code execution tool or Claude Managed Agents.
