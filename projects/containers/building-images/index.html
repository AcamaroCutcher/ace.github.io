A Dockerfile for a small web app

Here is a tiny Python web app that reports its own host name. Inside Docker that is the container's ID, so you can tell which container answered:

code/python-app/app.pyPython
"""A tiny web app: the smallest thing worth putting in a container (lesson 03)."""import osimport platformimport socket from flask import Flask app = Flask(__name__)  @app.get("/")def home():    return {        "message": os.environ.get("GREETING", "Hello from a container"),        "hostname": socket.gethostname(),  # inside Docker this is the container ID        "python": platform.python_version(),    }  if __name__ == "__main__":    app.run(host="0.0.0.0", port=8000)

And the Dockerfile that turns it into an image. Each line is one step:

code/python-app/DockerfileDockerfile
# Dockerfile for the tiny Flask app (lesson 03)FROM python:3.13-slim # don't write .pyc files, and print logs straight awayENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 WORKDIR /app # 1) dependencies first: this layer stays cached until requirements.txt changesCOPY requirements.txt .RUN pip install --no-cache-dir -r requirements.txt # 2) then the code, which changes oftenCOPY app.py . # run as an ordinary user, not rootRUN useradd --create-home appuserUSER appuser EXPOSE 8000CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]

Build and run it

Terminal (in the folder with the Dockerfile)shell
docker build -t hello-flask:1.0 .docker run --rm -p 8000:8000 hello-flask:1.0# http://localhost:8000 shows {"hostname": "3f2a…", "message": "Hello from a container", ...}docker run --rm -p 8001:8000 -e GREETING="Hi from a second copy" hello-flask:1.0

-t name:tag names the image, and the final . is the build context: the folder whose files COPY can see. The second run starts another container from the same image with a different setting; it reports a different host name.

Layers and the build cache

Build the image again without changing anything and it finishes almost instantly: every step shows CACHED. Change one line of app.py and only the steps from COPY app.py on are redone. If the Dockerfile copied everything first and then ran pip install, every code change would reinstall every package. The rule: put what changes rarely near the top and what changes often near the bottom.

Two more habits keep images small: clean up in the same RUN that made the mess (a file deleted in a later step still takes space in the earlier layer), and use --no-cache-dir with pip, as above. docker history hello-flask:1.0 shows each layer and its size.

CMD versus ENTRYPOINT

Both say what runs when the container starts. The difference is what happens to words you type after the image name:

  • CMD ["gunicorn", …] is a default. docker run hello-flask:1.0 python --version replaces it completely. Good for servers and general images.
  • ENTRYPOINT ["hello"] is fixed, and your words become its arguments: docker run hello-f Ada runs hello Ada. Good for images that wrap one program, like a command-line tool.

Write both in the JSON form with square brackets. The plain form (CMD gunicorn app:app) runs through a shell, which then doesn't pass on the stop signal, so docker stop waits ten seconds and kills the program.

Multi-stage builds: compile big, ship small

Compilers are large but the programs they make are small. A multi-stage build compiles in one image and copies only the result into a second, slim one. Here a Fortran program is compiled with the official GCC image:

code/fortran/hello.f90Fortran
! hello.f90 -- a program to compile inside a container (lesson 03)program hello  implicit none  character(len=64) :: name  if (command_argument_count() > 0) then    call get_command_argument(1, name)  else    name = 'world'  end if  print '(3a)', 'Hello, ', trim(name), ', from a container!'end program hello

Download hello.f90

code/fortran/DockerfileDockerfile
# Multi-stage build (lesson 03): compile with the full toolchain, ship only the program. # Stage 1: GCC with gfortran (well over a gigabyte)FROM gcc:14 AS buildWORKDIR /srcCOPY hello.f90 .RUN gfortran -O2 -o hello hello.f90 # Stage 2: a small Debian with just the Fortran runtime libraryFROM debian:bookworm-slimRUN apt-get update \ && apt-get install -y --no-install-recommends libgfortran5 \ && rm -rf /var/lib/apt/lists/*COPY --from=build /src/hello /usr/local/bin/helloENTRYPOINT ["hello"]

The same pattern works for C, C++, Go, Rust and Java, and for websites: build the JavaScript with a Node image, then copy only the finished files into nginx.

Sharing images

An image on your laptop is only useful to you. Push it to a registry and anyone (or any server) can docker pull it. On Docker Hub the name is USERNAME/IMAGE:TAG; on GitHub's registry it is ghcr.io/USERNAME/IMAGE:TAG (log in with a personal access token that has the write:packages scope).

Terminalshell
docker login                                     # Docker Hub; or: docker login ghcr.iodocker tag hello-flask:1.0 USERNAME/hello-flask:1.0docker push USERNAME/hello-flask:1.0

A Mac with Apple silicon builds arm64 images, and most servers are amd64. Build for both at once with buildx, which pushes one tag that works on either:

Terminalshell
docker buildx build --platform linux/amd64,linux/arm64 -t USERNAME/hello-flask:1.0 --push .
Never bake secrets into an image Anything you COPY or set with ENV stays in the image's layers, even if a later step deletes it, and anyone who pulls the image can read it. Pass secrets when the container runs (-e, --env-file), or at build time with RUN --mount=type=secret (lesson 08).

Exercises

  1. Build hello-flask, change the greeting text in app.py, and rebuild. Which steps say CACHED? Now add requests to requirements.txt and rebuild: which steps run now?
  2. Swap the two COPY steps around so everything is copied before pip install. Repeat exercise 1 and compare the build times.
  3. Remove USER appuser, rebuild, and run docker run --rm hello-flask:1.0 whoami. Put it back and run it again.
  4. Change the Fortran Dockerfile so the second stage is FROM gcc:14 too, and compare the sizes with docker images.
